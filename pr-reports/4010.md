# PR Report: Version update navigation and reload feedback

PR: [#4010](https://github.com/6529-Collections/6529seize-frontend/pull/4010)
Branch: `agent-prxt/reliable-update-pill` → `main`

## Summary

Desktop browsers show the existing rocket as the first lower sidebar item, directly above Search, when an update is available. The standard sidebar row supplies the icon spacing, hover/focus behavior, collapsed Update tooltip and expanded Update label. It replaces the desktop toast. Mobile browsers, including tablets in desktop browsing mode, keep the full toast.

Native app users get a small rocket in a curved attachment above Home using `rocket-refresh-small.png`. It lives inside the navigation dock and follows its movement, hiding, and phone scroll scale. The attachment uses the dock’s existing translucent black background and backdrop blur; the rocket uses only its own refresh-arrow circle. The update dock retains main’s shadow radii, offsets, opacity and stacking order. Outer shadows exclude the entire interior. A continuous CSS contour clips the glass and active navigation highlight, avoiding overlapping clip shapes at the attachment join. WebViews without CSS `shape()` support retain the SVG clipping fallback. CSS on the dock drives its dimensions, the attachment and the rocket together; no resize observer, React geometry state or regenerated image masks track animation frames. Without an update, the original main dock styling is used directly. Home continues to navigate home.

All three update controls share the same reload flow: a static rocket, the one-line localized message Updating to the latest version, and three animated dots. The cover embeds a 180-pixel transparent WebP derived from the current rocket directly in its server-rendered HTML, removing the separate image request during document replacement. The embedded artwork is approximately 18 KB; regenerate it with `./bin/6529 exec node scripts/generate-version-reload-image.cjs` when the source rocket changes. A source-hash test catches outdated artwork. The cover image is decoded when an update becomes available. Tapping waits for image readiness before showing the outgoing cover, with a one-second fallback for unavailable images. A short-lived session marker restores the server-rendered cover before hydration. Once the incoming app shell is ready, the cover waits for its rocket to decode and paint, then clears as a whole. Restricted storage does not block reloads, and a 30-second timeout prevents the cover trapping a failed startup. Reduced-motion preferences disable dot animation.

## Refresh behavior

One shared version check drives the prompt and native pull-to-refresh. With an available update, a completed pull fully reloads the page through the same helper as the update button, preserving the route and wave reading position when available. Otherwise the gesture keeps its content-refresh behavior.

The explicit `showNewVersionToast=true` preview flag also reacts to client-side query changes, so a mobile share/deep link can trigger the compact update control after the app has already mounted.

## Release configuration

Production requires the existing `ANNOUNCED_VERSION_ENDPOINT` to return a valid ready announcement. Missing production configuration, invalid configured endpoints, network errors, and timeouts no longer fall back to the responding server's version. Local/staging environments with no announcement endpoint retain live-instance comparison. No new environment variables are introduced.

## Risks / Follow-Ups

The reported attachment seam over bright media still needs confirmation on the affected device. The continuous-contour change targets the clipping boundary without changing paint values; the original seam was not reliably reproduced in the isolated fixture. The compatibility fallback retains the previous clipping behavior on older WebViews.

The original Android report of an update persisting after tapping the refresh control has not been reproduced on a device. The existing release-announcement publication and version-ordering policy remains in place. Production compilation requires runtime environment configuration that was unavailable locally; visual evidence uses an isolated component fixture rather than a live native app. The frontend can restore the cover from the first incoming HTML paint; any native WebView blank before that paint needs device verification.
