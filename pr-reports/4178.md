# PR Report: Mobile battery savings and chat video playback

PR: [Frontend #4178](https://github.com/6529-Collections/6529seize-frontend/pull/4178)
Branch: `agent-prxt/mobile-battery-savings` → `main`
Related PRs: [Backend #2140](https://github.com/6529-Collections/6529seize-backend/pull/2140)

## Summary

Reduce unnecessary mobile background work and require Play for Wave/DM chat videos across desktop, mobile browsers, and Capacitor. Display server-generated still previews while keeping video sources withheld until Play.

## What Changed

- Pause mobile media loading, rendition checks, unread polling, typing activity, wave timers, and socket health timers while inactive. Refresh state on return and preserve the existing browser notification connection behavior.
- Chat starts one video at a time. Offscreen/hidden playback pauses and returning waits for Play. Preserve the selected rendition, position, mute choice, and volume through virtualization within the open chat, including delayed metadata and HLS readiness.
- Derive the backend JPEG key from an owned drop upload URL. Load previews independently from video, retry missing previews within a bounded period only while visible and active, discard stale callbacks, and retain successful previews. External videos do not get guessed preview URLs.
- Use preview dimensions for chat layout before video metadata, preserving portrait proportions. NFT, homepage, leaderboard, and submission playback rules remain unchanged.
- Update user documentation and Help Bot knowledge for previews, processing delays, and older videos without thumbnails.

## Rollout / Compatibility

Deploy backend #2140's `dropVideoConversionInvokerLoop` and template-read policy before this frontend. No API/model change, new frontend environment variable, dependency, or native-shell rebuild is introduced by the preview addition. Existing CloudFront configuration is reused.

New uploads get previews after processing. Existing videos are not automatically backfilled; missing previews keep Play available without downloading video to extract a frame. An optional old-video replay requires a separate backend operation. Leaving the chat or reloading may reset playback memory.

## Risks / Follow-Ups

Verify real MediaConvert JPEG output during the authorized backend rollout. A black first frame can produce a black thumbnail. Local browser execution and device power profiling were not performed; Safari/WKWebView and quantified battery savings still need device evidence. Representative poster/no-video-before-Play browser coverage is registered in the local composer sandbox across desktop, mobile, and native simulations, without weakening retention or submission layout expectations.
