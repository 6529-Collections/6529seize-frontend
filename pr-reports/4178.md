# PR Report: Mobile battery savings and chat video playback

PR: [Frontend #4178](https://github.com/6529-Collections/6529seize-frontend/pull/4178)
Branch: `agent-prxt/mobile-battery-savings` → `main`
Related PRs: [Backend #2140](https://github.com/6529-Collections/6529seize-backend/pull/2140)

## Summary

Reduce unnecessary mobile background work and require Play for Wave/DM chat videos across desktop, mobile browsers, and Capacitor. Display device-generated still previews with server generation as fallback while keeping video sources withheld until Play.

## What Changed

- Pause mobile media loading, rendition checks, unread polling, typing activity, wave timers, and socket health timers while inactive. Refresh state on return and preserve the existing browser notification connection behavior.
- Pace competition-context lookups at four starts per second with at most two in flight, preserving cancellation and authorization checks. React Query focus pauses queued work in inactive browser tabs and follows the existing native-app activity signal; cancelled queued work never reaches the API. This limits the per-drop request bursts introduced by the competition integration in [#4153](https://github.com/6529-Collections/6529seize-frontend/pull/4153).
- Attach shared activity listeners only while the mobile policy applies. Desktop retains capability detection for hybrid-device transitions without notifying every mobile consumer on tab switches; native visibility uses the existing native listener.
- Hydration uses the server activity/device snapshot before applying the actual mobile policy; video sources remain withheld during that transition, including hidden mobile-browser tabs.
- Outside a chat memory provider, retain playback only for the current source, so revisiting a slideshow item starts fresh instead of restoring an old position or skipping a finished video. Chat retains its per-source memory across virtualization.
- Chat starts one video at a time. Offscreen/hidden playback pauses and returning waits for Play. Preserve the selected rendition, position, mute choice, and volume through virtualization within the open chat, including delayed metadata and HLS readiness.
- Capture one local frame while drop-video multipart parts transfer and include a bounded JPEG in completion, without a new UI step. Stop capture after eight seconds, cancellation or backgrounding; unsupported codecs and failures omit it. The API stores a validated device poster before completing the original video; the converter skips JPEG capture when that poster exists.
- Initialize competition context focus binding lazily on the first lookup, preserving background queue pauses while avoiding import-time side effects in unrelated consumers.
- Prefer device `_device.jpg` posters, then MediaConvert’s one-second capture (`_poster.0000001.jpg`) and retain its first capture (`_poster.0000000.jpg`) for older or sub-second videos. An inspected upload confirmed that a black first frame can look like a missing poster.
- Derive the backend JPEG key from an owned drop upload URL. Load previews independently from video, retry missing previews up to 20 times with backoff to one check per minute only while visible and active, discard stale callbacks, and retain successful previews. External videos do not get guessed preview URLs.
- Keep video measurement and responsive sizing in a dedicated hook so the player remains within the source-file size limit. Use preview dimensions for chat layout before video metadata, preserving portrait and square width limits as well as proportions through metadata readiness. NFT, homepage, leaderboard, and submission playback rules remain unchanged.
- Update user documentation and Help Bot knowledge for previews, processing delays, and older videos without thumbnails.

## Rollout / Compatibility

Deploy backend #2140's converter/policy and API completion handler before this frontend, verifying the API execution role can store device posters and inspect pending uploads. The optional completion field and generated models are updated; no new frontend environment variable, dependency or native-shell rebuild is introduced. Existing CloudFront configuration is reused.

Supported device uploads normally have previews when posted; failed attempts get backend previews after processing. Existing videos are not automatically backfilled; missing previews keep Play available without downloading video to extract a frame. An optional old-video replay requires a separate backend operation. Leaving the chat or reloading may reset playback memory.

## Risks / Follow-Ups

An earlier `/waves/create` hydration failure left the CI dev server unreachable on retries; it did not recur in the instrumented run, and its cause remains unconfirmed. Temporary server and memory diagnostics have been removed. The dev launcher retains the correction that a signaled Next.js exit is unsuccessful. Browser expectations, retries, timeouts, and pack selection are unchanged.

Verify real MediaConvert JPEG output during the authorized backend rollout. Clips still black at one second can still have black thumbnails. Already-generated black first-frame posters require a separate replay or re-upload after the converter update; existing posters remain compatible. The standalone local capture check exercises actual Chromium decoding and JPEG encoding without starting the app. App-level browser packs and device power profiling were not run; Safari/WKWebView and quantified battery savings still need device evidence. Both device and generated poster/no-video-before-Play, delayed arrival without refresh, and preview/playback geometry browser coverage is registered in the local composer sandbox across desktop, mobile, and native simulations, without weakening retention or submission layout expectations.

Large lists can fill in competition details progressively while lookups are paced. This limits one request source and cannot guarantee API capacity when other clients share the quota. Runtime pacing requires verification after an authorized deployment; Main Stage test readiness and API diagnostics are maintained separately in [#4201](https://github.com/6529-Collections/6529seize-frontend/pull/4201).
