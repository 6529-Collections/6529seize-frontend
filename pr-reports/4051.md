# PR Report: Canonical URLs and sitemap coverage

PR: [#4051](https://github.com/6529-Collections/6529seize-frontend/pull/4051)

Branch: `codex/seo-canonical-sitemap` → `main`

## Purpose

Give four public pages explicit canonical and Open Graph URLs, and include more public pages and published Museum entities in the generated sitemap. This is a discovery and metadata change; it does not redesign these pages or change minting behavior. No backend changes or new configuration are required.

This report is the manual checklist to use when testing is requested. The steps below are expected behavior derived from the implementation, not a record of completed staging or production checks. Recheck the deployed version and current PR diff before using it, especially if other SEO PRs have since landed.

Local Museum browser checks use a fixed US country-check response so publication rendering does not depend on geolocation of the test runner's IP. This fixture applies only to the exact read-only country-check endpoints on loopback test runs. Staging and production still use live country lookups; Museum content and artwork requests retain their existing checks.

Museum media acceptance waits for the Research card inventory and includes lazy images added while earlier images load. It requires the image count to stay unchanged for 500 ms after settling each batch, with a 30-second inventory timeout. Every discovered image must still load successfully, and unresolved media messages remain failures.

## Before testing

1. Confirm that the environment being inspected contains #4051's changes. An open PR or a successful build alone does not mean the website has been updated.
2. Start on staging. Use production URLs only after the change has been deployed there.
3. Use a normal desktop web browser for the mint-page check. Existing native iOS purchase restrictions are outside this change.

## 1. Check the four page URLs

Open each staging link below. After production deployment, repeat with the production link. Each page should render its intended content without an unexpected redirect, error page, or Museum publication-unavailable message.

| Page | Staging URL | Production URL / expected production canonical |
| --- | --- | --- |
| Museum Network | [Staging Museum Network](https://staging.6529.io/museum/network) | [Production Museum Network](https://6529.io/museum/network) |
| Open Data | [Staging Open Data](https://staging.6529.io/open-data) | [Production Open Data](https://6529.io/open-data) |
| The Memes mint | [Staging mint](https://staging.6529.io/the-memes/mint) | [Production mint](https://6529.io/the-memes/mint) |
| Tools API | [Staging Tools API](https://staging.6529.io/tools/api) | [Production Tools API](https://6529.io/tools/api) |

For each page:

1. Open **View Page Source**, or inspect the main document's **Response** in the browser's Network panel after a reload. Inspect the server-returned HTML, not only the browser tab title.
2. Find the actual `<link rel="canonical" ...>` element and `<meta property="og:url" ...>` element. Do not count references inside serialized scripts as duplicate elements.
3. Expect exactly one canonical element and one `og:url` element, both pointing to the full URL for that page on the environment being tested. They must not point to `/`, a different page, or the wrong environment.
4. Repeat with `?utm_source=seo-check` appended to the URL. Both metadata URLs should still be the clean URL without that query string.

Example: on staging Open Data, both values should be `https://staging.6529.io/open-data`. In production, both should be `https://6529.io/open-data`.

## 3. Inspect the generated sitemap

The current staging deployment runs `base-build` without the sitemap `postbuild` step, so it does not publish these XML files. Until that deployment gap is fixed, mark the staging sitemap check as unavailable and inspect a production-build artifact or repeat the checks after production deployment. A missing staging sitemap alone does not show that this PR's sitemap generation is broken. The steps below apply when the generated files are present.

1. Open [staging sitemap](https://staging.6529.io/sitemap.xml). If it is a sitemap index, open each child sitemap needed to find the entries below.
2. **Keep browsing the staging host:** the index and its entries use `https://6529.io` by design. Copy a child sitemap URL and replace only its origin with `https://staging.6529.io` to inspect staging's generated file. Otherwise clicking it can silently inspect the old production file.
3. Expect XML rather than an error/login page. Search the actual `<loc>` elements across the child files for the four newly admitted static paths, each appearing once with the production origin:

   - `https://6529.io/about/open-metaverse`
   - `https://6529.io/open-data`
   - `https://6529.io/the-memes/mint`
   - `https://6529.io/tools/api`

4. Confirm `/museum/network` remains included. Its explicit page canonical is new; the Museum homepage itself is not a newly added sitemap route.
5. Check the Museum families below against the accepted publication used for that build. Examples come from the PR's publication-shaped fixtures; use them when those records are still published canonical pages, otherwise select a currently published record of that family. Do not treat fixture counts as permanent production totals.

| Family | Example path |
| --- | --- |
| Work, existing coverage | `/museum/network/works/6529NM-W-0001` |
| Artist, existing coverage | `/museum/network/artists/casey-reas` |
| Organization, expanded coverage | `/museum/network/organizations/art-blocks` |
| Project, expanded coverage | `/museum/network/projects/century` |
| Curated acquisition, expanded coverage | `/museum/network/acquisitions/the-system-in-seven-states` |
| Acquisition program, expanded coverage | `/museum/network/acquisition-programs/keys-and-gates` |
| Research publication, expanded coverage | `/museum/network/research/the-system-in-seven-states` |

Each qualifying record must occur once at its canonical route. Admission requires `entityStatus: published`, `pageExposure: canonical_page`, and a canonical route matching the supported entity family. A work must use an ID matching `6529NM-W-` plus four digits and have the same slug as its ID. Other supported families require a slug.

Check that source-ID aliases such as `/museum/network/works/6529NM.2026.001.01` and `/museum/network/acquisition-programs/6529NM-AP-01` are absent as sitemap entries. Archived, reserved, relational-only, malformed, or mismatched records must not be admitted through the entity graph. Use the accepted publication records to assess exclusions; the sitemap alone cannot prove a record's publication status.

Finally, open a representative entry from each available family on staging by replacing only the origin. Expect the intended public page without a 404, 500, unavailable-publication state, or unexpected redirect. The sitemap should list the canonical destination, not a legacy alias that redirects to it.

After production deployment, repeat using [production sitemap](https://6529.io/sitemap.xml) and production destinations. Production page canonicals and sitemap origins should now agree.

## 4. Optional Google confirmation after production deployment

In [Google Search Console](https://search.google.com/search-console), select the production property, paste a production URL from section 1 into **URL Inspection**, and run **Test live URL**. Expect successful fetching and no accidental indexing prohibition on these public pages. Inspect the returned HTML to confirm the canonical and `og:url` values.

In the **Sitemaps** report, inspect the site's submitted sitemap and any fetch/parse errors. The report should eventually show successful processing; it need not update immediately after deployment.

Google's selected canonical is shown in the indexed report after crawling, not predicted by the live test. Immediate indexing, changed rankings, or Google choosing the requested canonical are not pre-merge acceptance criteria. See Google's [URL Inspection documentation](https://support.google.com/webmasters/answer/9012289?hl=en).
