# PR Report: Notifications and wave entry loading

PR: [#4407](https://github.com/6529-Collections/6529seize-frontend/pull/4407)

## Summary

Notifications now use one loading surface throughout route preparation, wallet restoration, profile loading and the first feed fetch.

Direct drop links open the detail surface immediately while the requested drop loads. The shared pending panel says `Loading…` and failures say `This content could not be loaded.` so the copy stays neutral until the post or submission is identified. Previous cached drops cannot flash during the handoff, and failed loads offer retry and close actions. Retrying a drop or its wave metadata shows loading feedback while the request runs. The existing Default, Memes and Quorum submission layouts are retained. Ordinary wave entry keeps the outer layout’s sidebar placeholder; direct drop entry shows only the detail loader. Pending panels focus Close, scope Escape to their own surface, and preserve keyboard focus through dismissal or the loaded-detail handoff. Default and Memes panels also expose retry when wave metadata fails.

Ordinary wave entry uses one quiet conversation frame for the route, pending wave metadata and the public-to-interactive handoff. JavaScript-enabled browsers select it before hydration, avoiding the temporary simplified posts view. The semantic public post text and links remain in server HTML and stay readable with JavaScript disabled; browsers without the scripting media feature retain the readable preview until hydration. Existing server feed seeding, filters and access checks remain intact. Chat readiness is scoped to the matching mounted wave, including after revisiting or reloading it; remembered non-chat sections retain their own loading states. The initial thread loader stays quiet inside chat; failed requests retain retry recovery and already loaded replies.

Wave drop links retain the server-provided drop title throughout hydration and background chat updates. Opening or switching drops releases the wave title observer, including before its navigation cleanup. Closing the drop restores the wave title. Existing crawler and social metadata remain intact.

The waves list stays pending during wallet/profile restoration, including before the wallet address becomes available, avoiding false empty-collection messages. Loading clears when the guest or connected identity settles. The route loader fills the available width and uses the same desktop sidebar breakpoint as the wave shell. Media continues loading inside its own frames after chat appears.

## Scope

Frontend UI and loading handoffs, localized loading/error copy, product documentation and help-index updates. The dynamically loaded wave shell uses the same route-aware loader, preserving the detail-loading surface during shell initialization. Existing API contracts and server-side visibility filters are preserved. Interactive chat waits for wallet/profile resolution even when the URL already selects a wave, preserving the previous layout’s auth gate.

## Risks / Follow-Ups

Wallet restoration with real accounts and broader native journeys still need runtime verification.
