# Drop Forge launch and EMMA processing

PR: [Frontend #4207](https://github.com/6529-Collections/6529seize-frontend/pull/4207)
Companion: [Backend #2143](https://github.com/6529-Collections/6529seize-backend/pull/2143)

EMMA exposes one Process and Finalize action with durable progress and read-only
completed-list downloads. Refresh restores the same operation. The clicking
admin's authorization is handed to the backend; expired/denied access offers
Sign in to resume the same job without losing committed checkpoints. No new
service-account token or stored operator credential is introduced in the UI.

An existing pending, authentication-paused or completed process with different
phase inputs requires a distribution reset before processing can be submitted.
The button follows that backend guard; a failed/reset job can start a fresh
operation. This state transition is covered by component tests. The existing
admin read-only browser guard still covers the same Process and Finalize control;
this change adds no distinct browser interaction and does not require new E2E
coverage. Browser execution remains part of rollout validation.

Craft Launch queues opening work immediately after published metadata and
completed preparation. Republished metadata offers Update Claim. Launch shows
phase groups, per-action readiness failures, detected-complete skips and
transaction links. Ordinary earlier failures leave later scheduled groups
visible. Manual controls register exact transaction/category evidence and mirror
confirmed progress with automation, preserving pending hashes across retry.

Authorized recovery shows the exact action, wallet nonce, attempts and remaining
allocations. It supports same-nonce speed-up/cancellation, existing replacement
hash verification and reviewed remaining delivery after finalized settlement.
Requests retain their identity across uncertain responses; the UI never receives
signed transaction bytes or claims an uncertain airdrop was completed.

The global mention shortcut is @drops6529. Wave settings, suggestions and reserved
personal Quick Tags use the same canonical name; its recipient IDs are supplied
by backend environment configuration.

The companion backend uses `memesDistributionHandler` and `dropForgeLaunchHandler`
with targeted SQS work, per-drop one-time phase/Research schedules and
outstanding-work continuations. There are no permanent one-minute triggers or
feature-specific GitHub role variables. Existing UI status/API contracts remain
compatible with this dispatch change.

Internal infrastructure and operator setup stay in the maintained
[backend setup guide](https://github.com/6529-Collections/6529seize-backend/blob/agent-prxt/drop-forge-auto-launch-requirements/docs/drop-forge-auto-launch-setup.md)
and internal operator docs. Expanded launch/distribution internals were removed
from the public help corpus; public Memes phase windows and user-facing mention
behavior remain. Canonical and generated help/glossary artifacts are aligned.

Deploy the backend schema, transaction indexer, queue-owning handlers and API before this frontend;
keep preparation/automation disabled until the documented rollout checks and
manually supplied configuration are complete. Live on-chain signing, AWS dispatch
integration and production reporting still require the environment rollout.

The hub now starts Contract Admins collapsed and exposes Launch Automation.
Automatic launch and Automatic artist payment default Off. Only the creator owner
or configured claims administrators can change them; other Drop Forge admins see
read-only settings and can fund the wallet. The panel shows the configured KMS
address, optional verified ENS, chain, explorer link and ETH balance. Top Up ETH
reviews destination, amount and estimated fee before the connected wallet signs,
retains transaction hashes and tracks same-nonce replacements/cancellations for
reporting without sending another transfer.

Launch displays disabled-action reasons and frozen artist payout details. Research
and optional Pay Artist share the 18:00 Europe/Athens post-mint group. Manual Pay
Artist records exact transaction evidence through the shared coordinator. The
backend setup guide covers the new payout cap, default-Off settings, funding and
schema requirements. Live wallet/chain and browser flows require the documented
Sepolia rollout; no development server or deployment was started for this change.

The local production compile completed, but the full production build did not
finish its TypeScript stage and was stopped under memory pressure. The focused
type-check completed; the full-build completion gap remains.

Funding evidence registration preserves original-before-replacement ordering and
retains both hashes when the original acknowledgement fails. Pending-report status
uses the native output element; the wallet and permission controls are unchanged.

Research/Pay Artist show optional finalized supply evidence: RPC and DB totals,
comparison block, completed indexing progress and retry eligibility. Missing values
stay unavailable. The backend gates both transfer and already-satisfied decisions,
backs disagreements off at 1/5/15 minutes, and verifies settlement before completion.
The internal docs and README describe the one-time 17:15 preview and fresh 18:00
execution, exclusively in the dedicated operations wave. Existing mint-announcement
destinations are unchanged. The companion backend's new indexing coverage is a
rollout prerequisite. No public help-corpus expansion is introduced.

The added evidence is a readonly data display, covered at the component layer.
The existing `admin-destructive-guards-readonly.spec.ts` (`admin-guards-readonly`
pack) and critical-shell access guards remain valid; no selector or interaction
contract is changed. Those browser specs were inspected but not executed locally. Browser execution and live chain/wave checks remain rollout
validation; the previously documented full local production-build gap remains.

## Shared calendar foundation

This PR targets main and builds on the merged [frontend calendar #4454](https://github.com/6529-Collections/6529seize-frontend/pull/4454) and [backend calendar #2247](https://github.com/6529-Collections/6529seize-backend/pull/2247).
Manual Launch controls use saved UTC phase windows for accepted launches and await
the launch lookup before enabling claim writes. New unmanaged claims use bundled
calendar defaults. Backend #2143 owns stage policy, reduced runtime configuration
and frozen launch scheduling. Receiver mismatches remain blocking.

The calendar foundation uses relative consumer imports for Core subtree
compatibility, preserving the Electron shared-folder alias. The same calendar is
bundled locally in the renderer after the normal frontend sync; no runtime
calendar dependency or Core checkout modification is introduced.
