# Drop Forge operator controls and EMMA processing

PR: [Frontend #4207](https://github.com/6529-Collections/6529seize-frontend/pull/4207)
Companion: [Backend #2143](https://github.com/6529-Collections/6529seize-backend/pull/2143)

EMMA uses one Process and Finalize action with durable processing, completed and
failure states. Refresh discovers the current job. Subscription CSV downloads
read the completed job's paginated lists rather than repeat preparation writes.
Normal phase/component exports and existing allocation/photo controls remain.

Craft adds Launch after publication and Update Claim after republished metadata
changes. Launch queues initialization immediately using the backend's fixed mint
calendar. Loaders reflect backend work, blocked errors remain visible, and dirty
or unpublished edits cannot submit. Metadata updates preserve mint configuration
and completed airdrops. Edition/distribution changes need separate review.

The existing Launch page shows durable action progress and transaction links.
Manual writes acquire a backend lease before prompting the wallet; accepted
hashes carry the action category and persist locally until submitted successfully,
including across refresh. Confirmed evidence credits only remaining allocations.
Unknown wallet outcomes keep automation paused for explicit hash reconciliation
or safe cancellation. Automation updates the existing completed-category flags.

The shared action timeline includes automated Research at 17:15 Europe/Athens
the day after minting begins. It targets `min(310, Craft edition size)` minus the
fresh on-chain minted total, skips an already-filled target, reconciles confirmed
manual Research, and updates the existing Research completion flag. Craft and
on-chain maximum mismatches block execution. Pay Artist remains manual.

Generated API contracts match the companion backend. @dropforgers6529 renders
as a reserved global mention; recipient IDs are resolved by the backend. User
guidance and help knowledge describe processing, immediate launch, metadata
updates, phase timing and manual recovery.

Automation/preparation remain default-disabled. Wave/profile IDs, credentials,
KMS key, wallet funding and on-chain admin grants are manual deployment inputs.
Live KMS/chain/wave execution and end-to-end browser flows were not exercised;
no local development server was started. No deployment or main merge is included.

Completed-list access requires the three current phase IDs; missing or stale
job evidence stays unavailable. Manual hash persistence is tied to the write's
local attempt and lease, and cancellation clears only that attempt. Callback
identity changes cannot retrigger the confirmed-work refresh. Null leases remain
an explicit legacy/unmanaged permission, while managed conflicts reject BEGIN.

Published help and glossary artifacts are regenerated from the canonical corpus.
Fallback errors use the locale message system; transaction links are shown only
for mainnet and Sepolia. Manual writes stop before prompting when recovery
storage is unavailable. If storage fails after submission, the hook retains the
same hash in memory and retries backend registration without another wallet
write, warning the operator to preserve the hash if registration also fails.

Launch includes explicit transaction recovery: inspect the operational wallet,
nonce, attempts and exact allocations; request a speed-up or cancellation;
verify an existing replacement hash; and review delivery of outstanding work
following finalized cancellation/revert. Recovery stays pending until the backend
proves the winning transaction. A late original winner is completed without replay.
Cancelled transactions leave allocations outstanding. Requests retain their ID
across uncertain API results. No signed transaction bytes are exposed to the UI.

Existing `admin-destructive-guards-readonly` and `critical-shell` browser packs
continue to cover the unchanged access boundaries. Recovery confirmation and
state/API transitions have focused component coverage. Browser execution was
not performed because local development servers were not authorized.

Manual submission and persisted-proof recovery are separate hooks, keeping the
coordinated write flow within the function-size lint limit without a bypass.
Recovery outcome messages use native status outputs. Completed-list pagination
remains sequential because each response supplies the next offset.

Automation and recovery tests guard required fixture actions and recorded API
calls, and assign the generated recovery outcome enums directly. Assertions
continue to prove exact requests, retry identity and no replay after success.

Completed-list pagination follows each returned cursor through a sequential
reader while retaining non-advancing cursor rejection and exact row ordering.
Processing, manual writes and transaction recovery use the existing UUID library
so request IDs also work when a browser lacks native randomUUID. Launch schedule
guidance now describes the automation controls present in the UI.
