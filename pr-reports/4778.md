# Per-message reply collapse

[Frontend PR #4778](https://github.com/6529-Collections/6529seize-frontend/pull/4778) · [Backend PR #2422](https://github.com/6529-Collections/6529seize-backend/pull/2422)

## Summary

When wave-wide collapse is off, authors can choose **Collapse replies** from the desktop or mobile actions menu on their top-level chat drops. All existing and future replies to that drop appear in its thread for everyone. Authors can choose **Show replies inline** to reverse it.

## Frontend impact

- Readers use the existing thread expander. Links and in-chat jumps to nested replies can open the root thread.
- The timeline refreshes when reply placement changes. Individual collapse keeps the wave’s unread and notification rules. Pending sends and live thread counts use the root to keep replies together.
- The web client opts into the mixed timeline and uses the matching generated API types. The backend schema and API must deploy before the web client.

## Risks and follow-ups

The composer sandbox covers desktop and mobile reply placement with the same curation response shape as the API. Local browser validation requires starting the sandbox server. Unit tests cover compact WebSocket reply counts in inline waves and wave registration during cache eviction.
