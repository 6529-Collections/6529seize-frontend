# Personal settings as signed records (frontend)

[Frontend PR #5032](https://github.com/6529-Collections/6529seize-frontend/pull/5032) · [Backend PR #2546](https://github.com/6529-Collections/6529seize-backend/pull/2546)

## Summary

The settings writers learn to send the same change as signed records:
- follows;
- mutes, blocks and hidden drops;
- bookmarks;
- artwork alerts;
- pinned waves;
- wave notifications;
- preferences;
- mention shortcuts;
- push settings;
- EULA consent.

A device signs them with its existing device key, under its existing grant, so there is no new wallet prompt.

Which write goes out follows the API's mode (`GET /signed-records/mode`):
- **`legacy`, or the build flag off:** today's request only.
- **`shadow`:** today's request, then the same change as records marked as its companion. That second send is best effort and never shown.
- **`primary`:** the records only. A refusal shows today's message for its rule code.

Reads don't change: every list still comes from today's routes.

- **The submit queue:** one person's changes go one at a time, in the tab and across tabs, so the API takes them in signed order.
- **Large actions:** they are split into submits of at most 16 records.
- **Newer change on another device:** a change refused because another device's newer one came first is signed once more.
- **Pins:** a pin or reorder writes only the pins whose position moves.

## Frontend impact

- **For people:** nothing changes until the build has `NEXT_PUBLIC_FEATURE_PERSONAL_RECORDS=true`. Even then, the page writes as today while the API's mode is `legacy`.
  - In `shadow`, nothing visible changes.
  - In `primary`, settings save as records the device signs.
  - While the API pauses settings for the switch, a change isn't sent, and the person is told to try again shortly.
- **Proxies:** a proxy session is told that proxies can't change settings.
- **Config:** `NEXT_PUBLIC_FEATURE_PERSONAL_RECORDS=true` in the build. It is safe while the API's mode is `legacy`.
- **Rollback:**
  - The API's mode going back to `shadow` is enough. The page follows at its next mode read, at once on the next 409, or when a submit's answer isn't `primary`.
  - A build without the flag removes the code path.
- **API types:** `openapi.yaml` and the generated signed-records models match #2546.

## Frontend deployment

1. Merge and deploy #2546 first, with `PERSONAL_RECORDS_MODE` unset.
2. Merge this PR, then build with `NEXT_PUBLIC_FEATURE_PERSONAL_RECORDS=true`.
3. The API then moves to `shadow` and on to `primary` (the steps are in #2546). The frontend needs no further change.

## Tests

- The PR's 7 suites (209 tests) pass. They cover:
  - the mode handling in every mode, the pause, 409s and retries;
  - what each writer sends in each mode, and what a submit carries;
  - the keys record's reuse, and large actions across submits;
  - a burst of 50 follows saved in order;
  - refusals and their messages, owners and their cache, the pin positions, and the keys record cache's provider-key order.
- `tsc`, the Jest and Playwright type checks, ESLint on the changed files, and knip are clean.

## Known limits

- **Timed-out submits:** a submit that times out may still be saved by the API. The person is told to reload and check before trying again.
- **Pin positions:** these are planned against the pins the read returns.
  - A pin of a wave the person can't read now, or one another tab added since, can end up tied with a moved pin. Ties order by wave id.
  - The visible order is right, but a hidden wave that becomes readable again can show in an unexpected place.
