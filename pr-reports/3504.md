# PR Report: Send scoped deployment contributor evidence

PR: https://github.com/6529-Collections/6529seize-frontend/pull/3504
Branch: `agent-prxt/release-attribution-notes` -> `main`
Related PRs: https://github.com/6529-Collections/6529seize-backend/pull/1869

## Summary

Frontend staging and production notifications now send immutable,
operation-scoped contributor evidence for Release Bus deployments and derive
manual contributor scope from the exact approved deployment range.

## What Changed

- Sends the exact Release Bus train and operation identity from staging and
  production workflows.
- Marks Release Bus contributors with signed operation evidence and filters
  bots, automation identities, and case-insensitive duplicates.
- Derives manual staging and production contributors from the validated current
  workflow run, exact deployed SHA, latest approved baseline, bounded commit
  comparison, and merged pull requests targeting the deployed branch.
- Accepts contributor identities only when GitHub explicitly classifies the
  account as a user; organizations, Apps, bots, and unknown account types are
  excluded.
- Accepts the current manual run only while its successful notification step is
  live (`in_progress` with no conclusion), or as a completed successful replay;
  queued, failed, cancelled, or mismatched run evidence is rejected with a
  field-specific diagnostic.
- Requires the exact approved workflow file path as well as the workflow name,
  run ID, deployed SHA, and branch before deriving manual contributors.
- Bounds each GitHub evidence request and the complete contributor-evidence
  operation, with at most three rate-limit retries that honor retry headers
  only while the overall deadline permits.
- Aborts stalled or unavailable GitHub evidence, logs the exact timeout or
  retry-exhaustion reason, omits contributor fields, and still sends the CI
  notification through its separately bounded receiver request.
- Omits the Contributors row with a diagnostic when exact manual scope cannot
  be proven instead of trusting workflow input or guessing.
- Gives documented manual workflows the read-only GitHub permissions and exact
  staging SHA needed for attribution.
- Separates CI notification acceptance from release-note eligibility, enqueue,
  and queue-failure messages in workflow logs.

## Frontend Impact

- Workflows: Release Bus staging and production, manual staging, and manual
  production.
- Runtime application code: Not affected.
- Generated API/client: Not affected.
- User-visible behavior: CI wave deployment drops receive correctly scoped
  contributor mentions or GitHub links after the backend dependency is
  deployed.

## Config / Env

No new secrets. Existing workflow GitHub tokens gain read-only actions and
pull-request permissions for immutable deployment evidence.

## Compatibility and Rollout

Deploy backend PR #1869 first, then this frontend PR. The backend change is
compatible with the legacy notifier during the transition. No deployment,
Release Bus control change, notification replay, or release-note backfill is
included.

## Release Notes

The approved manual frontend production workflow remains intact. Release Bus
production notifications provide the exact workflow, run, SHA, train,
operation, and contributor evidence required by the corrected backend
release-note baseline and attribution contracts.
