# Encrypted messages: read from the relays while the server says they are primary

[Frontend PR #5027](https://github.com/6529-Collections/6529seize-frontend/pull/5027) · [Backend PR #2545](https://github.com/6529-Collections/6529seize-backend/pull/2545)

## Summary

While `GET /e2ee/me` says the relays are primary, the encrypted-messaging client reads a device's pending Welcomes, its log pages and attachment chunks from the relays instead of 6529.io. Writes still go to 6529.io.

The browser checks every record against the orderer's key and its stream's hash chain (allowing the positions an orderer's DEL names), every payload against its hash, that the relays hold the inbox head and the group's `last_seq` 6529.io names, and that the device is active. Any relay failure, unverifiable record or missing device grant makes that one call read from 6529.io, as today.

## Frontend impact

- **For people:** none in this rollout. The switch is the server's mode, and the backend keeps primary off (it needs an explicit opt-in). In off or mirror mode the client sends exactly what it sends now.
- **Rollback:** nothing to set on the frontend. The backend's `E2EE_RELAY_MODE` off or mirror stops relay reads within 5 minutes.

## Frontend deployment

1. The signed-records PRs, #4994 and #4997, and the backend PR's API (`GET /e2ee/me` gains the optional `relay` field, the inbox status `relay_head`).
2. This PR. No setting to change.
