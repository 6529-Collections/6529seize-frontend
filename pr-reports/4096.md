# PR Report: Device Farm Stability

PR: https://github.com/6529-Collections/6529seize-frontend/pull/4096
Branch: `agent-prxt/device-farm-stability` -> `main`

## Summary

Harden real-device Safari startup and distinguish infrastructure failures,
app/test failures, incomplete coverage, and recovered runs in mobile QA.

## What Changed

- Safari on iOS 16.4+ launches the target URL through WDA before debugger
  attachment. Both configured iPhones support the launch capability.
- Device-side navigation diagnostics retain offline and startup errors without
  replacing the original failure. Generic errors still require investigation.
- Per-device JSON reports expose selected/executed counts, setup failures,
  and recovery counts. The workflow verifies report completeness against the
  completed Device Farm run's device-job count.
- Unreadable archives are distinguished from missing or invalid device results.
  Navigation recovery counts reset for each reporter run. The standalone test
  bundle has its own Knip analysis scope and dependency manifest. Its commands
  use the bundled Mocha entry point explicitly, supporting analysis with only
  frontend dependencies installed.
- Web test, command, and navigation retries are disabled. Independent page
  checks verify a blank document before loading the destination once, preventing
  the previous page's delayed router effects from racing the next direct load.
  Readiness checks origin/path and rendered content together. Empty/skipped
  suites, missing evidence, planning/packaging failures, and requested packs
  that cannot run all fail the aggregate report.
- Device pools, cadence, native smoke/fuzz behavior, and all app assertions
  remain intact. No application routes, API contracts, or dependencies change.

## Risks / Follow-Ups

The Safari launch change still needs real-device validation. The acceptance
procedure is ten fresh sequential web runs against the same branch head,
covering both iPhones and all three Android devices with every selected test
executed and no recovery. Keep failed attempts in the evidence record; revise
the fix and restart the streak if the problem recurs. The existing daily
schedule provides longer-term evidence afterward.

[The first branch run](https://github.com/6529-Collections/6529seize-frontend/actions/runs/36099676558)
passed Android and all seven iPhone 16 assertions without recovery. The iPhone
SE passed seven assertions after retrying navigation from `/the-memes` to
`/network`, so the strict workflow correctly failed. Its logs show the previous
page updating sorting query parameters after the next navigation was accepted.
The blank-document barrier addresses this interference; real-device validation
of that follow-up remains outstanding. Older or unknown iOS versions retain
the prior launch path. No app navigation behavior is changed by this harness fix.

The local Museum rendering lane now serves checksum-verified copies of the
18 accession image derivatives. This addresses the observed 502 on the Larry
Towell image proxy request without weakening media, responsive-selection, or
geometry assertions. The fixture rejects unknown media URLs and leaves deployed
staging/production requests live. It covers the six works behind the accession
proxy; other image sources remain live. Local rendering results do not certify
upstream availability. The gate retains traces on its first failure.
