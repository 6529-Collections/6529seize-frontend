# Open in 6529 Mobile

PR: [#4037](https://github.com/6529-Collections/6529seize-frontend/pull/4037)
Branch: `agent-prxt/open-in-app-banner`
Base: `main`

## Summary

Mobile website visitors can open their current page in 6529 Mobile from a compact banner above the site header. The banner uses `public/6529bgwhite.svg`, the title `6529 Mobile`, a `Get the app` link, an `Open` button, and a dismiss button, with vertically centered controls and no divider between the buttons.

## User Behavior

- Dismissal hides the banner for seven days in the same browser, including reloads and other tabs. If local storage is unavailable, dismissal survives client-side navigation but can reset on a full reload.
- `Open` captures the current path, query parameters, and fragment at the time of the tap. Native cold-start and foreground handling preserve that destination, including repeated query values.
- Android Chrome uses a package-targeted intent with a destination-preserving browser fallback. Other browsers attempt the registered custom scheme directly.
- `Get the app` opens the appropriate store. Installation does not automatically transfer the destination through the store; return to the browser page and tap `Open` afterward.
- The website remains usable without acting on the banner. The banner is hidden inside 6529 Mobile and 6529 Desktop and on handoff, authentication, access, and app-wallet routes.
- `/open-mobile` remains a separate handoff page with `Open app`, `Download`, and `Continue in browser`. It does not automatically launch the app or display an indefinite `Opening` state. Invalid destinations fall back to the home page with explanatory copy.

## Configuration and Compatibility

The existing optional `MOBILE_APP_SCHEME` frontend setting is reused; an absent or invalid value falls back to `mobile6529`. Native URL reception also accepts the released app's `mobile6529` scheme. Android intents target the existing `com.core6529.app` package.

The inspected iOS and Android app configuration already registers the custom scheme. This implementation requires no native configuration change. Universal Links and verified Android App Links remain a separate enhancement requiring domain association files, native configuration, and an app release.

## Risks and Follow-Ups

Production build validation is blocked by an existing CSS Modules error in `app/about/AboutRouteLayout.module.css:15`: a standalone global selector is rejected as non-pure. This file matches `main` and is outside this feature's changes.

Custom-scheme attempts cannot reliably distinguish an absent app from a blocked or cancelled launch. A browser may show an error or remain on the page. Neutral help and explicit store/browser actions remain available; there is no timed store redirect or installation claim.

Real-device iOS/Android validation remains outstanding because native device tooling was unavailable. Browser screenshot verification was also unavailable. Before release, check:

- Safari and Android Chrome with the app installed and absent.
- Cold and warm launches to waves, drops, profiles, and the home page, including query parameters and fragments.
- Blocked or cancelled opening, Android browser fallback, and direct retries from the handoff page.
- Banner alignment at narrow widths, page-header height after dismissal, and continued browser navigation.

New strings use the existing English locale fallback. No backend, API, database, or desktop-specific changes are included.
