# PR Report: Emoji usage memory and quick-reaction fallback

PR: [#4083](https://github.com/6529-Collections/6529seize-frontend/pull/4083)

Quick reactions and reaction chips now use the same lazily loaded history writer as the emoji picker. Opening a picker and selecting another emoji no longer overwrites newer quick-reaction counts from the same page session. Picker selections count once and refresh the quick-reaction row, including selections made in the composer.

Desktop and mobile show up to three distinct available emojis ranked by usage. Saved identifiers that resolve to the same emoji occupy one slot. Native emojis render independently of the custom emoji list. If no saved emoji can be displayed, one thumbs-up button appears and submits thumbs-up rather than a hidden, unavailable reaction.

Existing browser-local history is retained with no storage migration. Previously overwritten counts cannot be recovered; history does not sync between devices. There are no backend, API, dependency, or configuration changes.

Quick-reaction accessible names and desktop tooltips identify the selected emoji. The action text and fallback name follow the browser locale. Emoji resolution stops after three usable entries, skips unavailable history entries without a fixed cutoff, and reuses results across unrelated renders.

## Risks / Follow-Ups

The native-mobile responsiveness capture for `/the-memes` timed out before the native body marker and shell were ready; `/network` also needed a screenshot fallback. These routes and shell initialization are outside the reaction change. The runtime cause remains unconfirmed and needs a separate investigation; this PR does not alter the shared capture harness or app shell.
