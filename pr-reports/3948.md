# PR Report: Profile-scoped mobile notification cleanup

PR: https://github.com/6529-Collections/6529seize-frontend/pull/3948
Branch: `agent-prxt/profile-scoped-mobile-notifications` → `main`
Related PR: https://github.com/6529-Collections/6529seize-backend/pull/1987

## Summary

Mobile reads remove only delivered notifications belonging to the matching profile and confirmed read by the server. Other profiles and newer unread notifications remain in the tray. Global tray cleanup is reserved for explicit sign-out-all. iOS badge counts remain server-driven.

## What Changed

- Reconcile notification-page/grouped reads, navigation refreshes, app activation, native registration readiness, and successful wave reads on iOS and Android. A delayed registration or recovery retries cleanup without waiting for another read or activation.
- Capture the profile/auth session and delivered snapshot; abandon cleanup after session changes or lookup failures. Missing records and unread counts of zero alone are not proof that an individual entry is read.
- Match push `target_profile_id` and `notification_id`, with a versioned Android tag fallback supplied by backend PR #1987. Preserve the native ID and Android tag when removing an entry.
- Keep exact aggregate iOS badge updates in the backend. No native package or mobile release is introduced.
- Persist native logout revocations in secure storage before removing credentials. Single logout removes the profile/device registration; sign-out-all sweeps the installation, including stale profiles missing locally. Other devices keep their sessions.
- Determine native logout safety from the session runtime, including before UI hydration. If durable cleanup cannot be queued, retain credentials for retry.
- Load the native push plugin only during native logout cleanup, preserving web authentication module initialization. Reject revision overflow before changing the stored revocation outbox.
- Use an AbortController timeout compatible with older native WebViews and settle preparation failures so waiting registration callbacks can retry.
- Reconcile pending cleanup on activation, connectivity recovery and before fresh registration. Installation revisions reject old registration requests and make revocation retries safe after a later login.
- Retry failed or partial connected-profile registration on activation and connectivity recovery even when no logout job completed. Keep successful registrations and defer old-target cleanup until every connected profile registers.
- Tie registration caching to the login session and cancel obsolete read lookups on profile/auth/proxy changes.
- Generate the installation revocation API models and update the mobile push guide and Help Bot corpus.
- Keep the registration OpenAPI revision ceiling aligned with revocation and backend validation (`4294967295`).

## Risks / Follow-Ups

- Cleanup passes are serialized per provider. Overlapping triggers coalesce into a fresh pending pass so reads completed during a lookup are still reconciled. Each pass performs one authenticated lookup per distinct matching delivered entry, with at most four concurrent requests. An unavailable record is preserved rather than inferred read.
- Legacy Android entries without identifiable metadata remain for manual dismissal. Android launcher dots/counts follow the launcher; no numeric badge guarantee is made.
- Reconciliation runs while the app executes for the active profile. A desktop read can update the iOS badge through APNs, but does not guarantee immediate selective tray removal while the app is closed.
- Before rollout, verify installed-device iOS 2 → 1 → 0 badge behavior, foreground/background delivery, rapid reads/new pushes, and Android ID/tag removal. Backend delivery remains asynchronous and best effort.
- Publish backend PR #1987's installation schema via `dbMigrationsLoop`, then its push worker and API, then the frontend. The existing secure-storage plugin is reused; no native package or app release is introduced.
- Offline revocations remain pending until the app reconnects; clearing app data can lose that outbox. Unreadable secure storage retains local credentials rather than silently losing cleanup.
- Conflicting legacy tokens no longer block a replacement phone: its push UUID is bound to the native device identifier, with a fresh credential and revision sequence. Old logout jobs remain intact and retry independently. Token-scoped migration removes only provable old delivery targets; unproven tokens remain registered for owner/support cleanup. Failed logout on the current installation still blocks its own registration.

- Logout before the first server-side push registration requires a valid native refresh session to record a logout fence scoped to the installation secret. This does not claim the device ID or block registration with another credential. If that session is missing, revoked, or expires before offline reconciliation, cleanup stays pending until ownership can be verified; ordinary registered installations continue using their installation secret or legacy token proof.

## Phone-transfer recovery

The existing native Device plugin distinguishes a restored backup on another phone. The first upgrade from an unbound UUID also creates a fresh namespace. Migration retains each old job's credential, revision and sessions, retries namespaces independently, and never acknowledges a different installation's job just because its revision matches. Current native tokens are never injected into old logout requests. Profile notification preferences carry forward through authenticated registration without overwriting later edits.

Roll out the updated backend API before this frontend. The API adds token-scoped cleanup and preference-copy fields; older APIs reject them. No native dependency or mobile binary release is added. Token-scoped cleanup retires only the old matching badge target, and replacement registration queues a new-device correction. Actual iPhone delivery still needs an on-device check after rollout.

`tests/surfaces/native-shell-readonly.spec.ts` was reviewed: they do not exercise native Device/secure-storage/FCM callbacks. These recovery contracts belong in focused native-adapter and lifecycle tests; no browser expectation changed and no local development server was started.

Connected profiles are registered with their own saved authentication without switching the visible account. Old token-scoped cleanup starts only after all currently connected profiles register successfully. If a saved session has expired, reconnect that profile; its old delivery target is preserved in the meantime. During migration, old and new targets can briefly coexist.

Recovery rollback must preserve device bindings and the outbox containing multiple installation identities. Reverting to the older single-installation storage reader is not a safe rollback after migration; ship a compatible client fix and keep the recovery API available until pending work drains.

After old-target cleanup succeeds, the app requests a fresh badge correction for the replacement installation. Push delivery and badge presentation still depend on the operating system.


## Launch/resume badge correction

After connected-profile registration succeeds, the iOS app requests the current
installation badge on launch and resume through the companion backend's
`push-notifications/installations/badge-refresh` endpoint. The backend computes
the aggregate across registered profiles and sends its existing badge push.
Nothing is marked read and no native package or app release is required.

Requests use current installation proof, refuse stale auth/token/device state or
pending current-device logout, coalesce while in flight and time out after 15
seconds. Failures leave notification state alone; later activation can retry.
Android retains profile-scoped tray cleanup and launcher-dependent badges.
Deploy the companion API addition before this frontend. Actual badge correction
remains dependent on APNs delivery and needs an installed-iPhone check.
